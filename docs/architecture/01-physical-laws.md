# 五大顶层框架逻辑（物理定律 · 司法解释）

> 本文件是 AGENTS.md 第 1 节的“司法解释”：对每条定律给出判定标准与反例。
> AI/开发者审代码时，对照本文件逐条核对。

## 定律 1：通信契约优先

**判定标准**
- 接口入参/出参、事件消息体，都能在 `contracts/` 找到对应定义；
- 服务代码引用的类型来自 `contract_sdk`，不手写 wire 字段。

**红线反例**
- 业务代码里出现 `payload["UserId"]`、`user_id`、`uid` 混用；
- 接口返回结构没有契约支撑。

**补充细则**
- 事件也是契约：`event_name` 带版本（`user.created.v1`）；
- 线上契约 ≠ 领域模型：契约管线上格式，领域模型管业务逻辑。

## 定律 2：数据主权单向流

**判定标准**
- 每张表有且只有一个 Owner 服务；
- 跨服务引用只存 ID；
- 需要对方数据时：低峰走聚合/BFF，高频走事件读模型。

**红线反例**
- 订单服务直接查用户服务的表 / 跨库 Join；
- 订单表冗余存用户昵称、手机号（未走事件读模型条款）。

**和解条款（Read Model）**
> 允许消费方通过订阅事件维护派生只读表；该表归消费方所有；
> 更新只能来自事件，禁止实时 Join 源服务；副本字段必须来自事件契约。

## 定律 3：权限二维防线 + 信任边界

**判定标准**
- 网关：白名单 + 角色（功能级）；
- 业务：默认拒绝 + 属主/租户/ACL（数据级）；
- 业务不重复查菜单树/URL 权限。

**红线反例**
- 业务服务信任客户端直接传来的 user_id（未经过网关注入）；
- 数据查询“默认放行，个别拦截”。

**信任边界细则**
- 生产：`TRUST_PROXY_HEADERS=true` + 网关与服务间 mTLS/服务网格；
- 服务只读 `X-User-Id / X-User-Roles / X-Tenant-Id`，其余身份信息一律不信。

## 定律 4：最终一致性 + Outbox

**判定标准**
- 跨服务副作用：本地事务 + outbox 落库 -> 提交 -> relay 异步投递；
- 副作用接口带 `Idempotency-Key`；消费者幂等（at-least-once）；
- 失败走退避重试 + 死信，不反向回滚主服务。

**红线反例**
- 事务提交前直接发 MQ（消息丢失窗口）；
- 写 XA/两阶段提交；
- 消费者不幂等导致重复扣款/重复建单。

## 定律 5：可观测性基因

**判定标准**
- 服务依赖 OpenTelemetry（`traceparent`），不自造 TraceID 头；
- 调用下游/发消息时透传 trace；日志为 JSON 且带 request_id/trace_id；
- 暴露 `/health/live` 与 `/health/ready`。

**红线反例**
- 用线程局部变量传 trace（asyncio 下必错）；
- 日志不带 request_id/trace_id，排错只能看机器。
